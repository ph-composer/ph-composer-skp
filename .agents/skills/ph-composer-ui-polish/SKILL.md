# PH-Composer UI Polish

Treat each screen as another view of one application, not a standalone visual redesign. Preserve behavior and domain language while making the initial state quiet, legible, and predictable.

The patterns come from the predecessor, PH-Navigator for SketchUp, whose UI kit was transplanted into this repository. [references/patterns.md](references/patterns.md) lists local paths separately from predecessor-only screens not yet built here. The rules are the same for both.

## Priorities

Design for the consultant using the tool. Each change should make the next step obvious, keep the work surface still, and remove words and controls the user does not need. Simple and consistent beats clever. Push back on any direction, including the owner's, that works against the end user, and say why before building it.

Geometry first, then action: the user selects geometry and then chooses what to do to it, one attribute at a time. A modal action-first tool is the secondary route unless the feature's plan records why it is better. The rule is in `context/TECH_STACK.md` under "Rules for later features".

The UI kit is meant for reuse by other teams. A screen pattern that only works because of one feature's data shape is a defect in the kit, not a local convenience.

## Design System

The settled kit is published as the [PH-Composer Design System](https://claude.ai/artifact/77GLrkZxtkxo9TksTbvodL), a Claude artifact private to the owner: the colour tokens under the panel's CSS names, the type styles, spacing and radius, the brand book and static renditions of the kit parts. The stylesheets under `src/ph_composer/html/` remain the authority; the artifact is a reading aid and may lag them. It does not hold live components or the two Builders' drawing styles.

After a change to the kit (a token, a type style, a shared part or its states), re-sync the artifact from `main` in the same piece of work and say in the report that it was done, or that it was not and why.

## Establish the baseline

1. Read the repository `AGENTS.md`, the active feature plan or UI spec, and any local index or instructions file governing the paths in scope.
2. Read `planning/ui-baseline/README.md` for the screen in scope: it rules on every visible part of the predecessor's screen as keep, change, remove or add.
3. Read [references/patterns.md](references/patterns.md). Inspect the current source before relying on the listed examples because the app will continue to evolve.
4. Inventory every visible region, action, state, warning, and selection. Distinguish primary work from secondary reference information.
5. Record the existing behavior that must survive: commands, disabled states, focus return, Escape handling, Undo boundaries, and host-owned workflows.

## Polish in this order

1. **Hierarchy:** Give the page one clear title, restrained metadata, and prominent primary metrics. Use size, weight, spacing, and grouping before introducing color. Metric labels use the standard PH names with proper subscripts (U<sub>w</sub>, U<sub>w,installed</sub>) and carry the unit, so the value line is just the number (an em dash glyph with a tooltip naming what is missing). Explain a distinction users often miss with a small info icon and hover bubble, not a longer label. Never put a constant caption or internal readiness text under the title; show why a primary action is blocked beside that action: `ui.reasonButton(action, reason)`, an alert icon that opens the reason in an anchored bubble, never a page notice and never a footer far from the action. General hints go in a help button. Titles rename in place: the title becomes a field with check and cross icons, Enter applies, Escape cancels, leaving applies; never open a modal for one text field. New and Duplicate act at once under a free default name and open the new title for renaming, where the record draws something the user can then work on (an Assembly, a Window Type); a record that is only numbers (a Material, a Frame, a Glazing, a Psi-Install Type, an Attached zone) keeps a form in the shared dialog, with its required fields marked and its disabled Create saying what it waits for; Delete confirms in the shared dialog. Per-record Rename, Duplicate and Delete live on that record's sidebar row as small icon buttons revealed on hover or focus, not in a header menu; the row renames in place with the same check and cross. Menu rows show a short state value (a unit id, not a long label) so they never overflow. In a list of setting choices, mark the current one (`aria-pressed="true"`) like the active sidebar row: `--interaction-highlight-tint` background with teal text and border, unchanged on hover, never a plain unmarked button.
2. **Layout:** Establish stable page regions. Keep headers, sidebars, toolbars, work surfaces, inspectors, and status areas spatially consistent with accepted screens. When one page contains distinct peer jobs rather than one staged task, give them shared sub-tabs and show one work surface at a time. Do not stack an editor after a separate inventory or review table as though it were their footer. Every tab row, top-level or nested, uses the shared subtabs nav with an `aria-label`; never style a feature-local tab bar. Tabs inside one page share that page's heading, which holds the active tab's primary New action when present. A tab body starts with its action bar (view controls, muted stats, tab-specific settings), never with a second page title.
3. **Actions:** Show one primary text action when the page has a dominant next step. Group frequent adjacent actions in a compact toolbar. Use recognizable icons with tooltips and `aria-label`s. Put infrequent lifecycle, secondary, and destructive actions in the shared overflow menu. Keep active progress and cancellation visible. Show only actions the current selection can use. When two actions are mutually exclusive states of one property (Glazed or Empty), use one button that offers the change available and repaints its icon and label from the selection; with a mixed selection, the first selected item decides.
4. **Progressive disclosure:** Start with the minimum needed to orient and begin. Reveal contextual tools on selection and put configuration choices in anchored bubbles or menus. Do not conceal required state or the only route to a core action. If a disclosed surface owns an active transaction, draft, Save, or Cancel action, keep that surface visible and lock navigation that would hide its controls until the transaction ends.
5. **Sidebars:** Reuse the shared expanded/collapsed structure and behavior. Preserve selection while collapsed. At narrow widths, degrade to a compact horizontal control instead of consuming the work surface.
6. **Feedback and decisions:** Render transient information and warnings in an overlay layer so late messages do not reflow the page. Preserve the notice's intrinsic height inside zero-height overlay layers and verify single-line and wrapped messages visually. Give floating notices an accessible Dismiss control; a notice also closes on Escape (after any open bubble or dialog). A disposable success confirmation (tone `success`, a check mark beside it) fades by itself after three seconds, held while the pointer or focus is on it; informational feedback fades after the user's next meaningful pointer or keyboard interaction. Warnings, errors, and instructions needed for an active tool remain until resolved or explicitly dismissed, so an instruction is never sent as `success`. A newer message replaces an older one and stops its clock. Do not apply one timeout to every message. Use inline panels for contextual detail that can coexist with the current task. Use a blocking modal when the user must review consequences and choose among actions before returning to the work surface. Keep the surface stationary behind the modal; preserve Escape, Cancel, focus return, and the operation's existing transaction boundary. Every dialog from `formDialog` carries the same top-right close, which does exactly what Escape and its Cancel do, and returns focus to what opened it. The footer runs right-aligned: Cancel, then a commit labelled with its consequence (Create, Save, Delete, Add library). A dialog whose actions apply at once has Close or Done, never a Cancel that pretends to undo them. Announce changing status accessibly. Give every floating notice a tone: `success` (white, with a check) for a completed action the user need not read again; `info` (the default, white) for instructions and tool directions; `warning` (yellow) for refusals and consequences the user should check; `error` (red) for failed requests and edits. Never show ordinary guidance in yellow. Record create, duplicate, delete and replace forms open in the shared form dialog, never in page flow above a table. Read-only detail about one row (its uses, its provenance) opens in a bubble anchored to that row's action. Editing one value (a dimension, a thickness) opens a small bubble headed by what the value is ("Column width"), holding the unit field and nothing else: Enter or leaving the field applies, Escape restores the value and Escape again closes, an invalid entry keeps the bubble open with its message. No Apply or Cancel buttons and no explanatory paragraph; accepted input formats go in the field's tooltip. Related destructive actions sit last as a danger-action row and confirm in a dialog that names exactly what goes. Every commit route (Enter, blur, a button) must reach the same submit path; test Enter, not only form submission. An edit that is one Undo step with a visible result (merge, split, flip, insert) applies at once, with no bubble restating what the button does. Confirm only when the edit discards something the user assigned (products, assignments, removed elements), in a form-dialog confirm that names exactly what goes. New records start with round, unit-aware defaults so they draw and work immediately (a Window Type at 1000 by 1500 mm, or 40 by 60 in); never create a record the user must complete before the drawing makes sense.
7. **Graphics and interaction:** Prefer unfilled geometry, crisp outlines, and a small semantic palette. An unfilled SVG shape only hit-tests its stroke, so give every selectable unfilled shape `pointer-events:all`; any state a user can set (Empty, a gap, a void) must stay selectable so they can set it back. Draw with an architectural line hierarchy: the overall profile or perimeter heaviest, element or component boundaries medium, and lines inside a component (frame sight lines, joints) lightest and greyer. Secondary annotation such as window operation lines is light, finely dashed and anchored to real geometry (glass corners and frame sight lines), never floating inside an inset. Use two highlight roles and keep them distinct: red `--drawing-highlight` for transient pointer states (hover, keyboard focus, insertion previews, drop targets) and teal `--interaction-highlight` for selection, the same teal as active sidebar rows and pressed controls. Do not rely on color alone. Hover outlines, selection outlines and drawing controls always render as an overlay above all geometry, so a neighbouring element never covers a shared edge or a control; in SVG, paint them in one layer appended after every element. A selected element takes a teal outline and the light `--interaction-highlight-tint` fill beneath its label, matching a selected sidebar row; stronger fills muddy glazing and material colors. Additive controls in a drawing (insert a row, column, layer or segment) stay hidden until the pointer nears the edge they act on, show one control at a time on that edge, and are named by their visual result ("Insert row above", "Insert column left"), never by an index or boundary number. Apply the addition at once with a round unit-aware default (500 mm or 20 in) as one Undo step, select what was created so the next step is obvious, and let the user adjust the size afterward. Never open a form to ask for a value the user can change directly. When the Model would refuse, say why on the control before the click. A modal drawing tool shows its state in three places at once: the pressed toolbar button, its icon, and the pointer cursor over the drawing. When the tool moves to its next stage the icon and cursor change together (eyedropper while picking a source, paint bucket while pasting). The tool stays active until Escape or a second click on its button. Escape unwinds one layer at a time: an open bubble or dialog, then an active tool (ending all its stages at once), then the drawing selection. It must work wherever focus landed: a drawing that re-renders on click drops focus to the page body, so also handle keys whose target is the body while the editor is visible. Toolbar glyphs follow the Lucide set: thin, round-capped outlines added to the shared registry with the ISC notice kept beside them. Text, labels, name pills, dimension lines and on-drawing controls are screen furniture: let them follow zoom only within a narrow band (0.9x to 1.25x of base size) while geometry scales freely, so zooming far out or in never makes them unreadable or oversized. A value the user still has to enter shows as a compact amber "?" pill that opens its editor and names the value in its tooltip and accessible label ("Set column 1 width"), never as clipped placeholder text; summary text that depends on it turns amber too. The same rule holds in forms and cards: flag missing inputs on the row where they belong (amber row tint, a small alert icon naming what is missing in its tooltip) rather than in a separate "To complete" list; only findings that belong to no single row collect below. Record cards holding several products or measured values are a compact grid: one column heading per quantity carrying its unit once in brackets, bare numbers in cells, an em dash glyph for missing or not-applicable values, 24px controls in 28px zebra rows, and a chevron on every control that opens a choice so it reads as a select. Inherited values (a model default) are muted with their source in the tooltip, not a trailing qualifier. A per-record toggle is a small icon toggle (filled when on, amber when the parent needs one chosen), not a sentence-long button. Dimension lines are a light rule beside each axis with a dot and short extension at every boundary, purely graphic. Editing a drawing never changes its zoom: fit the drawing when it opens, when the panel resizes and when the user asks (Fit drawing), then hold that scale through size edits, inserts, removals and proposed-change previews, so the one thing that moves is the thing the user changed. A drawing that outgrows the view scrolls; it does not shrink. Keyboard routes for drawing affordances are not a priority (owner, 2026-09-15); keep accessible names but do not add tab stops for them.
8. **Density and resilience:** Normalize gaps, control heights, borders, and radii. Check long titles, narrow panels, scrolling, wrapping, and zoomed layouts.
9. **Editable tables:** Treat the cell grid as the visual structure. Do not draw a second visible box around every input at rest. Let the row own hover (a light wash over every cell, never a cell tint or a chip's colour) and the cell own focus, selection, invalid, and pending states, while inputs remain borderless or visually transparent until their state needs emphasis. Keep the grid quiet: row hairlines, column separators only in the header, and a stronger heading row for each group of a tree. A focused cell must accept printable typing immediately; Enter and double-click are additional editing routes, not prerequisites. Preserve the first typed character. Keep identity and action columns aligned and sticky through selection and editing so activation never moves a cell. Make columns directly resizable by dragging their header edge, with a keyboard-operable separator and a quick reset. Preserve sticky-column offsets while widths change. Put secondary show/hide and reset choices in a compact anchored Table options menu; never expose a large in-flow Columns panel or a bank of width sliders. Validation and rejected-edit explanations must not increase row height: retain a clear invalid-cell marker and reveal a compact explanation anchored to that cell on focus or hover. Associate the message with the input for assistive technology, and clear it when the edit is corrected or cancelled.
10. **Words on screen:** Show glossary words from `context/UBIQUITOUS_LANGUAGE.md`, never internal codes, enum keys, calculation finding codes or record ids. Map stored kinds to labels at the view edge and keep the stored value as the data contract. When an id helps diagnosis, put it in a tooltip or an audit surface, not the visible label. Start control labels with a capital letter. Name a missing reference by what the user must do ("Missing product", "Choose a replacement"), not by its key. honeybee's face types and boundary conditions are shown by their glossary labels (Wall, Roof or ceiling, Floor; Outdoors, Ground, Adiabatic, Surface), and the stored honeybee string stays the contract.
11. **Stable lists:** Lists, card stacks and choices never reorder in response to selection, hover or focus. Keep a stable reading order. When a selection should focus attention, narrow or highlight the list in place and offer a one-click way back to everything.

## Never scallop a rounded edge

A thick left or right accent bar on a rounded element is banned throughout the app (owner, 2026-09-17): the radius clips the bar into a curved, scalloped edge. This covers `border-left`, `border-inline-start` and `box-shadow: inset Npx 0` accents of more than 1px. A solid full side border is fine on a square element; a rounded element carries its state in its fill, its label color and its icon instead.

A run of flagged rows must still read as separate rows. Carry the zebra into the warning tone (two tints of the same amber) and give each flagged row a hairline gap, rather than painting one continuous block.

## Page-header action rule

Use this order at the upper right:

- frequent editor actions as a visually grouped icon toolbar;
- configuration for the primary action as an icon that opens an anchored bubble;
- one labeled primary action;
- a standard ellipsis menu for infrequent type or record actions.

The ellipsis menu is not a dumping ground. Keep actions visible when their current state is important, when they are frequently used, or when hiding them would obscure the workflow. Destructive items belong last and retain a distinct destructive treatment.

## Screens that do not exist yet

Window placement and thermal bridge assignment have no accepted screen pattern; face assignment's (the Overview and the Classify tool) is recorded in `references/patterns.md`. They work in the SketchUp viewport with a native tool as much as in the panel. When designing one, start from the rules above, reuse the drawing-tool state rule (pressed button, icon and cursor change together; Escape unwinds one layer), and record the new pattern in `references/patterns.md` once the owner accepts it. Do not invent a second interaction grammar for the viewport.

## Verify the result

1. Add deterministic tests for structure, accessible names, state transitions, and preserved commands. Test the behavior rather than exact decorative markup.
2. Refresh the runtime manifest when packaged assets change and run the repository gates appropriate to the edit.
3. Follow `AGENTS.md` and the active agent's machine-level host-automation guidance before automating SketchUp. Use the established host bridge and native controls.
4. Check the screen in a real current host at representative dimensions. Capture evidence for hierarchy, overflow, open bubbles, hover or selection, warnings, and narrow layouts as relevant. A SketchUp window on an inactive macOS Space cannot be captured: keep verifying offline, never bring SketchUp forward over the user's work, and retake captures once the window is visible. Offline, use the preview page (`make ui-preview`): it is the real panel fed synthetic fixtures, so layout, overflow, bubbles and narrow widths can be captured there, and `make ui-checks` runs the browser checks (`make ui-deps` once installs their Playwright), and `make ui-gallery` captures every screen at every panel size for a design review; a review that sees one width misses narrow-panel defects. A browser check of a panel screen asserts, through `tools/ui-preview/support/pane_fit.cjs` at its `PANEL_SIZES` (1280 x 800, 420 x 732 and the 360 x 520 minimum), that the panel's own scroller never scrolls sideways and that floating controls never cover a table header and stay within reach of the pane's scroll; measuring the page alone missed two regressions (#179, #188). Every check runs through `tools/ui-preview/support/browser_evidence.cjs` (`check({ name, output }, ...)`), which fails it on any console error, page error, failed request or HTTP error it did not declare with `expect`, and writes a failure account beside its screenshots (`PH_COMPOSER_BROWSER_TRACE=on-failure` keeps a trace); a new check uses it. The preview does not replace the host check.
5. Run a fresh-process acceptance check when the feature gate requires it and the current model can be closed safely. Never discard a modified model to obtain a visual check.
6. After substantive implementation, use the repository's review ladder with the architecture review skill as the code rubric. Combine UI and architecture findings in the existing review where practical; use a stronger independent simplification review when the ladder requires it. Do not add an equivalent second review. Resolve material findings.

Report what changed, what passed, and any host checks deliberately omitted. Preserve unrelated dirty work.
