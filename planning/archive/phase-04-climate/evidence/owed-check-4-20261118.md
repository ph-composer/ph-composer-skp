## Host

SketchUp 26.1.188, Ruby 3.2.2, macOS, a fresh process launched by `host_bridge.py launch` on a fresh
copy of `_private/host/blank-template.skp` (`_private/host/oc4-20261118/never.skp`). The reads ran
in a probe loaded through `host_bridge.py eval` (`_private/host/oc4-20261118/read.rb` and
`api_probe.rb`); the raw answers are `item1-never.json` and `item2-api.json` beside them. The scratch
Model was not saved. SketchUp's default template (`Temp01a - Simple.skp`) reads the same location.

A file search for an already geolocated fixture under `_private/host/` and `tests/fixtures/` was not
determinable: SKP files are compressed, and the search missed the `GeoReference` dictionary that the
bridge then found in `blank-template.skp` itself.

## 1. A Model never geolocated

| Read | Value |
| --- | --- |
| `ShadowInfo["Latitude"]`, `["Longitude"]` | 40.018309, -105.242139 (Boulder, Colorado, the template's) |
| `ShadowInfo["TZOffset"]` | -7.0, a Float |
| `ShadowInfo["DaylightSavings"]` | false |
| `Model#georeferenced?` | false |
| `GeoReference` dictionary | `Latitude` 40.018309, `Longitude` -105.242139, `UsesGeoReferencing` false, `LocationSource` "Manual", `GeoReferenceNorthAngle`, `ModelTranslationX` and `Y`; no elevation |

## 2. A geolocated Model: an API stand-in, not Add Location

Inside one aborted operation on the scratch Model: `ShadowInfo` latitude 42.3233, longitude -73.3887
and `TZOffset` -5.0 were written, and `georeferenced?` stayed false. Writing the `GeoReference`
dictionary's `UsesGeoReferencing` true made `georeferenced?` true, while that dictionary's latitude
stayed 40.018309 and so disagreed with `ShadowInfo`. This proves which flag `georeferenced?` reads;
it does not show what Add Location writes, and the stand-in Model is not a CM06 fixture. After the
abort the attribute was undone and the `ShadowInfo` values were not.

No elevation is exposed in either place.

## 3. `TZOffset`

A Float that holds whatever is written: -5.0 and 5.5 were both kept. Setting `DaylightSavings` true
did not change it. Whether Add Location writes a whole number of standard hours, and for which
location, is not measured.

## 4. The result shape and board 22

`ph_composer.climate.site.geolocation` answers `{ geolocated, latitude_deg, longitude_deg,
hours_from_utc }`. It reads `ShadowInfo` latitude and longitude only when `georeferenced?` is true and
both are in range, and answers `hours_from_utc` null always until the dialog run proves the offset.
It never answers an elevation. Board 22 (`GeoUnavailable`) matches the host: an ungeolocated Model
reads "This SketchUp model has no geolocation."; it needs no redraw. Its line "and hours from UTC when
SketchUp has one" is not built; the dialog says it does not fill hours from UTC.

## Left for the conductor (needs SketchUp in front)

   choose Madrid, Spain (real offset +1, longitude about -3.7, so the offset is not a longitude

   longitude, `TZOffset` and `DaylightSavings`, and the `GeoReference` dictionary.
2. In a second scratch copy, Model Info > Geo-location > Set Manual Location with the same place, and
   the same read.
3. With the first Model, open the Climate tab's Set Location and press Read from SketchUp
   Geolocation: the latitude and longitude fill, elevation and hours from UTC stay empty.

If `georeferenced?` is false after a manual location, a user who set one sees "This SketchUp model
has no geolocation." That would be a product question for Ed, not a code change in this stage.
