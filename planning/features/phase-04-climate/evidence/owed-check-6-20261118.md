AUTHOR: Ed May, BLDGTYP, with Claude
ISSUE: none (local planning draft)

The [P4c-05 entry check](../phases/p4c-05-site-export.md#entry-checks), run in a scratch virtual
environment outside the repository: Python 3.11, the pinned stack of `pyproject.toml` (honeybee-ph
1.33.65, honeybee-core 1.64.65, honeybee-energy 1.123.23) and PHX 1.57.5 from PyPI. Each case puts
one honeybee-ph `Site` on the Building Segment of a 5 x 5 x 3 m box Room, writes the Model to HBJSON
and reads it back, then converts it with `create_project.convert_hb_model_to_PhxProject`,
`xml_builder.generate_WUFI_XML_from_object` and `metr_builder.generate_metr_json_dict`. All values
are synthetic. The probe script and its output (`run-1.57.5.txt`) stay in `_private/climate/owed-check-6/`.
The same cases gave the same values on PHX 1.57.0.

## 1. The PHX version (D4c-14)

`uv pip install --dry-run PHX` over the pinned honeybee-ph, honeybee-core and honeybee-energy resolves
to PHX 1.57.5 (2026-10-24), which requires `honeybee-ph>=1.33.65`. PHX 1.58.0 to 1.59.1 require

## 3. A provenance without the availability flags

The same `Site` with both flags `None` is refused before either writer runs: `ValueError: ... climate
is not ready for PHX conversion: provenance.monthly_data_available: monthly climate data availability
is unknown; provenance.peak_load_data_available: ... is unknown`. The Model writes the flags true for
every climate (Record::PROVENANCE_DEFAULTS), so an exported climate converts.

## 5. Found on the way (PHX, not this export)

METr's `lat`, `long`, `latB`, `longB` and `dUTCB` test the value's truth, so 0.0 or an offset of 0
is written as NaN: a `Location(0.0, 0.0, 5.0, 1, 0)` gave NaN for all three on PHX 1.57.5, and again on
PHX 1.59.1 (over honeybee-ph 1.33.68). No US site sits at
latitude or longitude 0, and an offset of 0 is not a US zone, so the Climate export is unaffected.
Recorded as a PHX follow-up in the P4c-05 report, not fixed here.

A second PHX gap, found by the round-trip test (step 8): PHX 1.57.5's `cleanup.merge_rooms` names the
Room it merges each Building Segment into after the segment's display name, and a honeybee Room
identifier may not hold a space. PH-Composer writes the Building Segment's name as its display name, so a
model whose segment is named `Main Building` fails conversion with `Illegal character " " found in honeybee
object identifier` before the site is read. The round-trip test renames the reference segments without a
space. Recorded as a PHX follow-up; the Site export is not the cause.

## 6. The round trip through the export (step 8)

`uv run --group phx pytest tests/python/test_site_phx_round_trip.py`, 2026-11-18: 2 passed. Board 18's
extraction over the two-Zone reference model, one Building Segment per Zone, converts to two PHX
variants, each with the site's latitude, longitude and elevation, the station elevation, climate zone
15, an empty `dUTC`, the monthly air and global radiation rows and the four peak-load cases, Cooling 2
equal to Cooling 1, in WUFI XML and METr JSON. A site alone reads back its Location, offset -6, over the
default climate. Without the group the test skips.
