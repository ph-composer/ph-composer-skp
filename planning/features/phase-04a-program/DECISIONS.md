# Phase 4a: findings and open questions

Findings are cited facts from the [research](README.md#read-order) that constrain any design.
Questions are the choices the interview must settle before a UI prototype commits to a shape. Each
question carries a leaning where the research points one way; a leaning is not a decision.

## Findings

| Id | Finding | Source |
| --- | --- | --- |
| F4a-01 | Nothing in PH-Composer writes a Program, load or schedule. Rooms fall back to Plenum and PHX's WUFI conversion fails without a People load. The smallest unblocking HBJSON is a People load on `Always On`, with the `Always On` ruleset and `Fractional` type limit emitted in the Model | [current state](research/ph-composer-current-state.md#1-the-gap), [programs](research/honeybee-energy-programs.md#3-model-emission) |
| F4a-02 | A honeybee ProgramType has eight slots: People, Lighting, ElectricEquipment, GasEquipment, ServiceHotWater, Infiltration, Ventilation, Setpoint. **Process is not one of them**: it is a list on the Room, in absolute W. honeybee-ph carries appliances as Process loads, and equipment Q12 gave appliances and their default set to the equipment packet | [programs](research/honeybee-energy-programs.md#1-programtype), [loads](research/loads-and-schedules.md#5-process-loadprocesspy) |
| F4a-03 | Program loads are normalised (per m² floor, per person, per m² exterior area, ACH). A per-Zone absolute value is a Room-level override whose per-area value depends on that Room's exported floor or exposed area. A Room with no floor face silently keeps a zero load | [programs](research/honeybee-energy-programs.md#2-room-inheritance-and-overrides) |
| F4a-04 | A program shared by many Rooms is locked on assignment; editing means duplicate and reassign. This maps onto PH-Composer's definition record plus Zone assignment, with overrides as a separate per-Zone record | [programs](research/honeybee-energy-programs.md#1-programtype) |
| F4a-05 | Schedules are shared by identifier across loads and programs and emitted once at Model level. Loading has no library fallback: every schedule and type limit named must be in the file. Each ScheduleDay needs its own identifier and belongs to one ruleset | [loads and schedules](research/loads-and-schedules.md#0-rules-an-exporter-must-follow) |
| F4a-06 | honeybee-energy never checks schedule values against their type limit, and Python and honeybee-schema disagree on several ranges. PH-Composer must validate values itself, to the stricter rule | [loads and schedules](research/loads-and-schedules.md#0-rules-an-exporter-must-follow) |
| F4a-07 | Residential occupants, bedrooms and dwellings live on `People.properties.ph`, not on the Room or building segment. PHX sums occupants and bedrooms per segment and counts units by dwelling identifier. Stage P4-12's "where are the per-Zone dwelling and bedroom counts stored" is answered by this packet | [PH stack](research/ph-stack-consumption.md#people-and-occupancy) |
| F4a-08 | PHX forks on the building segment's Phius `building_category_type`: residential reads PhEquipment and ignores ElectricEquipment and Process watts; non-residential does the reverse. PH-Composer authors no category; the export carries honeybee-ph's residential default | [PH stack](research/ph-stack-consumption.md#electric-equipment-process-and-appliances) |
| F4a-09 | The Infiltration load is the only airtightness path to WUFI, METr and PHPP. It stores m³/s·m² of exposed area at 4 Pa; PHX converts to q50 with exponent 0.65 and to n50 with net volume. Authoring n50 or q50 means the exporter inverts that conversion | [PH stack](research/ph-stack-consumption.md#infiltration-and-airtightness) |
| F4a-10 | The Program's Ventilation load is the Zone default that Spaces already say they inherit. PHX sums its four terms (ignoring `method`) and splits by Space floor share; any Space `_v_*` value overrides it | [PH stack](research/ph-stack-consumption.md#ventilation), [current state](research/ph-composer-current-state.md#2-zones-spaces-and-the-building-segment) |
| F4a-11 | Setpoints exist twice: the Program's Setpoint load (EnergyPlus only; PHX ignores it) and the building segment's `set_points` (PHX reads it). Hot water exists twice: the ServiceHotWater load (EnergyPlus only; PHX never reads it) and the honeybee-ph hot water system (Phase 4 equipment) | [PH stack](research/ph-stack-consumption.md#service-hot-water) |
| F4a-12 | Schedules have two representations. honeybee-energy rulesets (day profiles, weekday rules, date ranges) are what EnergyPlus reads. honeybee-ph operating periods (`properties.ph`) are what PHX prefers for WUFI utilization patterns; without them PHX derives patterns from the hourly values. PHX's ventilation branch requires the period names high, standard, basic and minimum | [PH stack](research/ph-stack-consumption.md#3-schedules-into-utilization-patterns) |
| F4a-13 | On the operating-period path PHX counts the daily window twice for occupancy and lighting: a Phius meeting room comes out at a relative factor of 0.229 instead of 0.5, and 1,260 lighting full-load hours instead of 2,750. The rulesets-only path is unaffected | [PH stack](research/ph-stack-consumption.md#3-schedules-into-utilization-patterns) |
| F4a-14 | PH-Composer ships only honeybee-energy's two default programs. honeybee-ph's 44 Phius programs all build on honeybee-energy-standards `2019::` base programs, which are not shipped (about 12 MB with schedules), so they cannot be built in the export runtime as pinned | [programs](research/honeybee-energy-programs.md#4-where-programs-come-from), [PH stack](research/ph-stack-consumption.md#4-where-ph-program-defaults-live) |
| F4a-15 | ScheduleFixedInterval has no `properties.ph` and PHX reads that block unguarded on People, Lighting and Ventilation schedules. Schedules PHX reads must be ScheduleRuleset | [loads and schedules](research/loads-and-schedules.md#schedulefixedinterval-schedulefixedintervalpy) |
| F4a-16 | The local honeybee-energy checkout adds ExhaustAir; the pinned 1.123.23 does not. Exhaust is out of scope until the pin moves | [programs](research/honeybee-energy-programs.md#baseline) |

| Q4a-04 | Scope | Setpoints: author on the Program, on the Building Segment, or both? | (a) Segment only (what PHX reads); (b) Program only, copied to the segment at export; (c) both, independent | (a) for PH output; a Program Setpoint only if EnergyPlus fidelity matters now |
| Q4a-05 | Scope | Hot water: author the ServiceHotWater load at all? PHX never reads it | (a) Yes, for EnergyPlus fidelity; (b) no, until a consumer needs it | (b), or a section with a "not used by WUFI/METr" note |

A PHX or honeybee-ph change belongs in those repositories |
| Q4a-09 | Code | Is a Schedule its own definition record shared across Programs, or owned by the load that uses it? | (a) Its own record kind, referenced by id (honeybee's model); (b) owned by the load, deduplicated at export | (a). | Q4a-10 | Library | Where do starting programs and schedules come from? | (a) Ship honeybee-energy-standards (about 12 MB); (b) a PH-Composer library file of Phius programs and schedules through the existing provider seam, built without the `2019::` bases; (c) manual entry only at first | (b) or (c). (a) brings DOE programs Phius users rarely need |
| Q4a-11 | Scope | Residential occupancy: where are occupants, bedrooms and dwellings authored? | (a) Per Zone on the Zones/Programs page, exported to People `ph` as Room overrides; (b) on the Program; (c) per Building Segment, split across Zones at export | (a).
